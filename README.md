# Итоговый проект "Менеджер паролей для Linux"

## как была настроена виртуальная машина
Виртуальная машина на основе *Oracle VirtualBox* была настроена на использование 2Гб оперативной памяти и диска с ёмкостью 20Гб. В качестве операционной системы была установлена *Ubuntu v24*.

## какие команды использовались
Использовались в основном команды установки пакетов вроде ```sudo apt install <pkg-name>```. Например, таким образом был установлен пакет sqlite3 для работы с базами данных. Остальные кманды перечислены в списке:
- создание пользователя ```sudo useradd```
- создание группы ```sudo groupadd```
- изменение прав ```sudo chmod ```
- изменение владельца и группы файла ```sudo chown```

## как запускать password_manager.py (с примерами add/list/get/del и генерацией пароля)
password_manager.py можно запустить командой ```python password_manager.py``` либо ```python -m password_manager```  находясь при этом в каталоге с самим скиптом. Выбор команд происходит в интерактивном режиме: после запуска скрипт переходит в бесконечный цикл опроса пользователя на предмет одной из четырёх команд. При добавлении (команда add) на втором шаге (после запроса логина) можно ввести свой пароль, а можно выбрать между 1 - слабый пароль или 2 - сложный пароль. При этом пароль будет сгенерирован автоматически.

## как пользоваться archive.py и usage_monitor.py
- archive.py - Скрипт нужен для запакоовки базы данных пароля в отдельный файл архива *.tar.gz* со сжатием. Архив сосдаётся рядом с файлом паролей (в том же каталоге)
- usage_monitor.py - Предоставляет отчёт об использовании основных команд менеджера паролей таких как add, get и del. Есть возможность очистки лога, для этого нужно указать в качестве параметра команду *clean*.

## какие проблемы встретились и как они были решены
При реализации логера для менеджера паролей встал вопрос на основе чего сделать декоратор для методов менеджера. Было два варианта:
1) на основе функции
1) на основе класса

Так как хранение паролей осуществвлялось в базе данных sqlite, то для хранения статистики, тоже было интересно запрятать данные в ту же базу в таблицу с суффиксом log. Таблица представляла из себя 2 колонки (действие и количество) и имела 4 строки - по числу методов с суффиксом "Oper" в классе менеджера. При этом функционал логера разростался на несколько функций отдельный доступ к которым был бы не желателен: можно было просто их импортировать и как то использовать. Для предотращения использования закрытых функций, было принято решение спрятать весь функционал логера в класс-декоратор, в котором все вспомогательные функции были представлены закрытыми (приватными) методами. Для этого в классе-декораторе реализованы методы:
- **__init__** - создание объекта класса-декоратора с передачей в него декорируемой функции (второй парметр). При этом объект декоратора заменял функцию.
- **__get__** - запрос декорированной функции из класса менеджера - в этом методе был сохранён сам объект менеджера для вытягивания из него подключения к базе.
- **__call__** - вызов декорируемого метода - объект класса декоратора сделали вызываемым (callable), чтобы он был похож на метод, который он задекорировал. Тут как раз происходит логирование операций. Исходя из названия метода - выбиралась та или иная строка в таблице лога и к значению количества добавлялась единица.
Проблема заключалась в том, что я не догадывался о нужности переопределения метода __get__, не откуда было получить объект менеджера, как резутат - неудача при запуске декорированного метода, которому нужен был объект менеджера в первом параметре (это метод класс с self в первом параметре). Ситуацию разрулил преподаватель, который указал на нужность переопределения метода __get__ в классе декоратора ибо декоратор в этом случае выступает свойством объекта менеджера.
